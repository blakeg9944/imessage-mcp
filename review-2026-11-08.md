# Review: imessage-mcp before the first live send (2026-11-08)

Read-only correctness review of `main` at `565c8ef`, checked against `SPEC.md`. Nothing was edited or committed.
`.venv/bin/python -m pytest` gives **188 passed**. Two findings were confirmed with scratch probes, which used the fake
osascript from `tests/fakes.py` on a copy of the synthetic DB. Nothing was sent, and no real dialog or real chat.db was touched.

**Bottom line:** the gates themselves are sound:
- The send and the dialog take their input as argv only.
- Cancel is the default, and a timeout counts as Cancel.
- The token is single-use and has an expiry.
- The echo check compares the right fields, and the send uses the previewed rows, not the echoed ones.
- LIVE together with NO_DIALOG is refused twice.
- The allowlist gates every read and send path.

I found **no way to send without the dialog, and no AppleScript injection.** The real risk is a **double text**:
- **H1:** a text can go out without being logged, which blinds the duplicate guard.
- **M1:** two overlapping batches can both pass the guard.

Both need an unusual event, so the first live send to a spouse or friend is low risk. Fix both before ward use.

---

## High

### H1. A sent text can go unlogged, so the duplicate guard can't see it
- **Where:** `imessage_mcp/sender.py:183-211`, together with `imessage_mcp/chatdb.py:93-105`.
- **What:** the log record is appended only at the very end of `_send_row` (line 211). That is after the osascript send
  and after the delivery poll, which can take up to 15 s.
  - `chatdb.connect` turns only *open* failures into `ChatDBError`. Any `sqlite3.Error` raised inside the `with` block
    escapes as a raw `sqlite3.OperationalError`. That covers `find_sent_row` in the poll and `max_rowid`.
  - `_send_row` catches only `ChatDBError`. So the exception skips `log.append` and aborts the remaining rows of the
    batch. The tool call then fails.
  - A failing `log.append` has the same effect, for example a full disk or a permissions problem on `logs/`.
- **Failure scenario (reproduced):**
  1. Messages is writing or checkpointing chat.db right after the send, and the read-only poll gets "database is locked".
  2. osascript has already sent the text.
  3. `confirm_send` raises, and `logs/sends.jsonl` has **0 records**.
  4. Claude reports an error. Blake asks to try again.
  5. `preview_send` passes the duplicate guard, because there's no log row. The member gets the same text twice.
  6. That member also has no `send_id`, so `check_interview_replies` can never track the reply.
- **Suggested fix:**
  1. Append an `attempted: true, status: "pending"` record *before* calling osascript. If that write fails, don't send.
  2. Append the final record afterwards. Have `live_sends` and `records` keep only the last record per `send_id`.
     `SendLog.get` already does this.
  3. In `connect`, convert `sqlite3.Error` raised inside the body to `ChatDBError`.
  4. In `_send_row`, wrap everything after a clean osascript exit in a broad `except Exception` that records
     `status: "unknown"` and still logs.

## Medium

### M1. Overlapping batches can both pass the guards, and the guards aren't re-checked after the dialog
- **Where:**
  - `imessage_mcp/sender.py:122-141`: `_recheck` runs *before* the dialog. Nothing re-checks between Send and the first
    osascript call.
  - `imessage_mcp/server.py:119-125`: tools run in worker threads. mcp 1.30 starts each request as its own task, so
    calls run concurrently.
  - `imessage_mcp/confirm.py:70-72`: `redeem`'s check-and-set is unlocked.
- **What:** the dialog can sit open for up to 120 s, and its row isn't logged until the send finishes. During that time a
  second preview and confirm of the same text pass every guard.
  - An interrupted tool call doesn't stop the worker thread, because `anyio.to_thread.run_sync` isn't cancellable. The
    first dialog stays up and can still send after Claude has moved on.
- **Failure scenario (reproduced by interleaving):**
  1. Claude calls `confirm_send` (batch A), and the dialog appears.
  2. Blake presses Esc in Claude Code, or the turn is interrupted, and says "try again".
  3. Claude runs `preview_send`. It passes, since A isn't logged yet. Claude then calls `confirm_send` (batch B).
  4. Two identical dialogs are now on screen. Blake clicks Send on both, thinking the first one hung.
  5. In the probe, A and B both report `delivered`, and the log shows 2 live sends of the same text to the same number.
  6. A's results never reach Claude, so its `send_id` is lost too. See L6.
- **Suggested fix:**
  1. Add one process-wide `threading.Lock` held from `redeem` through the final log write. While it's held, a second
     `confirm_send` returns "another send is in progress" and never shows a second dialog.
  2. Call `_recheck` again right after the dialog returns `Send`, before the first osascript send.
  3. Have `preview_send`'s duplicate guard also treat in-flight rows as duplicates. In-flight means redeemed but not
     finally logged, which the H1 pending record covers.

### M2. "Claude can't click this dialog" isn't true in this setup
- **Where:**
  - `imessage_mcp/dialog.py:4-5` (docstring) and SPEC §7.
  - README §"Never allow-list confirm_send", which covers auto modes but not computer use.
- **What:** the Claude sessions on this Mac have the computer-use tools (`mcp__computer-use__*`) and the browser tools
  available. A session granted full-screen control can click a `display dialog` button. The permission prompt is the
  other gate, and it disappears in auto or bypass mode. (This review session itself ran in auto mode.)
- **Failure scenario:**
  1. A session runs in auto mode with computer-use granted.
  2. A reply read through `get_replies` contains injected instructions ("text everyone on the list…").
  3. Claude follows them, so neither gate is a human.

  This is unlikely, since it takes two of Blake's own setup choices plus a model mistake. But the spec's central
  claim relies on it.
- **Suggested fix (docs, no code):**
  1. In the README, say that live sends must run in a Claude Code session with normal permission prompts, and with
     computer-use not granted or not connected.
  2. Reword the dialog docstring and spec to "Claude can't click this dialog *unless it has been given control of
     the screen*."
  3. Optional: remove `imessage` from sessions that have computer-use, using a per-project MCP config.

## Low

### L1. The allowlist isn't re-checked at `confirm_send`
- **Where:** `imessage_mcp/sender.py:102-141`. `confirm_send` takes no allowlist at all. By contrast, `server.py:90-92`
  says edits "apply immediately".
- **Failure scenario:**
  1. Claude previews a batch.
  2. Blake removes a member from `contacts.csv` within the 10-minute token window, for example after an opt-out
     reply, or because LCR showed the number was wrong.
  3. The pending token still sends to the removed number. The dialog still shows the name, so Blake has to miss it.
- **Suggested fix:** in `confirm_send`, reload the allowlist after `redeem`. Refuse the batch if any row's phone no
  longer resolves to the same contact and name.

### L2. `ok: true` when rows are `unknown`
- **Where:** `imessage_mcp/sender.py:142`.
- **What:** `ok` is false only when a row is `failed`.
- **Failure scenario:** osascript times out (`status: "unknown"`, `sent: false`), or the Mac is offline (no row in
  15 s). The top-level `ok: true` invites Claude to say "sent!"
- **Suggested fix:** set `ok` only when every row is `delivered` or `sent`. Add a one-line top-level summary such as
  `"1 delivered, 1 unknown (do not retry)"`.

### L3. The keyword guess has avoidable false hits, and text-style tapbacks aren't recognized
- **Where:** `imessage_mcp/replies.py:18-61`.
- **What:** precedence matches the spec: opt_out, then reschedule, then yes/no. These probe results are wrong:

  | Reply | Guess |
  |---|---|
  | "Not sure, let me check with my wife" | `yes` ("sure") |
  | "I can't wait!" | `no` |
  | "nope, won't stop me from coming, see you then" | `opt_out` |
  | "Please take me off this list" | `unclear` (missed opt-out) |
  | "No. Don't contact me again" | `no` (missed opt-out) |
  | `Liked "Could you meet … what about another time?"` | `reschedule` |

  The last row is how SMS (non-RCS) phones send a tapback: as plain text that quotes Blake's message. That text goes
  into the keyword match, so the guess comes from **Blake's own words**.
- **Failure scenario:**
  1. An Android member using SMS "likes" the invite.
  2. The guess is `reschedule` or `unclear`.
  3. Claude takes the hint and tells Blake they want another time.

  The guess is only a hint, hence Low.
- **Suggested fix:**
  - Detect `^(Liked|Loved|Disliked|Laughed at|Emphasized|Questioned) [“"]` text tapbacks, map them like the
    2000-2005 tapbacks, and keep the quoted part out of the keyword match.
  - Add `not sure` and `can't wait` exceptions.
  - Require `stop` to be followed by end of text, punctuation, `texting`, `messaging` or `it`.
  - Add `take me off`, `don't contact`, `do not contact` and `leave me alone` to opt-out.

### L4. The send script uses an account the check doesn't look at
- **Where:** `imessage_mcp/sender.py:26-30` vs `:38-42`.
- **What:** `check_account` counts accounts `whose service type = X and enabled is true`. But `SEND_SCRIPT` sends
  through `1st account whose service type = X`, with no `enabled` filter.
- **Failure scenario:**
  1. A Mac has an old, disabled iMessage account listed first, and a working one second.
  2. The check passes, and the send goes through the disabled account.
  3. The result is an osascript error, reported as `failed`, or a send from the wrong Apple ID.
- **Suggested fix:** add `and enabled is true` to both `1st account` lines in `SEND_SCRIPT`. Update SPEC §3 to match.

### L5. Phone normalization accepts numbers that can't exist
- **Where:** `imessage_mcp/phones.py:27-30`.
- **What:** any 10 digits are accepted.
- **Failure scenario:** a `contacts.csv` typo such as `1801555013` (a dropped digit) becomes `+11801555013` and is
  sendable. It can't reach a real person, but it surfaces only after the send, as `failed` or `unknown`.
- **Suggested fix:** reject an area code or exchange whose first digit is 0 or 1 (North American numbering rules).
  Report the row at startup.

### L6. A `confirm_send` that's interrupted loses its `send_id`s
- **Where:**
  - `imessage_mcp/server.py:119-125`.
  - There is no tool that lists recent sends.
- **Failure scenario:** as in M1 step 6. The text was sent and logged, but Claude never saw the `send_id`. So
  `check_interview_replies` can't be called for it. `get_replies` still works by phone.
- **Suggested fix:** let `check_interview_replies` accept phones as well as `send_id`s, mapping each to its latest
  logged live send. Or return recent `send_id`s in `preview_send`'s per-row `last_message` context.

### L7. Token expiry may not count time the Mac is asleep (verify)
- **Where:** `imessage_mcp/confirm.py:56`, which uses `time.monotonic`.
- **What:** on macOS, CPython's monotonic clock is, as far as I know, based on `mach_absolute_time`, which pauses
  during sleep. I didn't confirm this on Python 3.12.10.
- **Failure scenario:** a preview at 20:55 Saturday, then the lid closes, then a confirm on Monday. The token is still
  "fresh", but the preview's "last message in thread" is stale. Quiet hours and the duplicate guard *are* re-checked
  at confirm, so the impact is small.
- **Suggested fix:** also store `time.time()` at issue, and expire on either clock.

### L8. A late guid lookup can attach the wrong message
- **Where:** `imessage_mcp/replies.py:80-82`.
- **What:** for a send logged as `unknown` with no guid, `find_sent_row(..., after_rowid)` later takes the *first*
  outgoing row after that ROWID.
- **Failure scenario:** the server's send never created a row, and Blake later texted the member by hand. That manual
  text's guid becomes the anchor, so tapbacks on it count as replies to the invite.
- **Suggested fix:** take the late lookup only if the row's date is within about 60 s of the logged timestamp.

### L9. The demo-setup refusal only checks names
- **Where:** `imessage_mcp/config.py:62-64`.
- **What:** live mode is refused only when the contacts file is named `contacts.example.csv` or chat.db is under
  `demo/`.
- **Failure scenario:** `IMESSAGE_MCP_LIVE=1` with a synthetic DB copied elsewhere, such as a pytest tmp dir or
  `~/Desktop/chat.db`. The server starts live. The 555-01xx numbers are fictional, so the harm is small.
- **Suggested fix:**
  - In live mode, also require that `chat_db` resolves to `~/Library/Messages/chat.db`.
  - Or refuse when every allowlisted number is in the 555-01xx block.

## Checked and OK

- **The send uses argv only.** `SEND_SCRIPT` and `DIALOG_SCRIPT` are constant strings, and phone, text and service
  travel as argv. The call is in list form with no shell. `test_live_send_passes_phone_and_text_as_argv` uses quotes,
  backslashes, `end tell`, `$(…)` and newlines.
  - osascript's option parsing can't see a user string. The first argument after the script is always `+1…` (send) or
    the fixed dialog header (dialog).
- **The dialog fails closed** (`dialog.py`):
  - `default button "Cancel"` and `cancel button "Cancel"` mean Return and Esc both cancel.
  - The -128 error code (Cancel) returns `Cancel`, and `gave up` returns `Timeout`.
  - Any non-zero exit, `OSError` or subprocess timeout counts as not approved.
  - Only stdout exactly `Send` approves.
  - The dialog lists every row's name, number, service and text, plus DRY RUN, QUIET HOURS and REPEAT.
- **Tokens** (`confirm.py`):
  - The token is 128-bit random, single-use, and spent by any attempt, including a mismatch.
  - Expiry is checked, and an unknown token is refused.
  - The echo check compares row count, normalized phone, exact text, and the service (requested or resolved).
  - The dialog and the send use `batch.rows` from the preview, never the echoed list.
- **Delivery check:**
  - It matches by ROWID greater than the pre-send `MAX(ROWID)`, with `is_from_me = 1` and no tapbacks, and never by
    text.
  - Status order is error, then delivered, then sent, then unknown, as in §9.
  - There's no SMS fallback.
  - An osascript timeout is logged as attempted, so the duplicate guard counts it.
- **Config:**
  - Live mode needs exactly `IMESSAGE_MCP_LIVE=1`.
  - LIVE together with NO_DIALOG is refused in `config.load` and again in `confirm_send`.
  - Bad quiet-hours or Sunday values refuse to start.
- **Guards:**
  - The quiet-hours window wraps midnight correctly.
  - Sunday is blocked by default.
  - Both guards are re-checked at confirm.
  - The duplicate guard normalizes case, whitespace and curly quotes, and ignores dry-run and `failed` rows (per the
    handover).
- **The allowlist gates every read and send:**
  - `preview_send` calls `allow.require`.
  - `get_replies` calls `allow.require` per phone.
  - `check_interview_replies` calls `allow.require` on the logged phone.
  - Threads are 1:1 chats only, from handles that normalize to that phone.
  - Email handles never match. Shared-household numbers are blocked. A missing `contacts.csv` means an empty
    allowlist.
  - No tool takes a chat ID, guid or free-form query. One minor exception: `target_texts` looks up tapback targets by
    guid across the whole DB. Those guids come only from rows already in an allowlisted thread.
- **Replies:**
  - Replies are anchored at the send timestamp, which is taken just before osascript runs. The window ends at the
    next logged live send.
  - Tapbacks count only toward the guess when their target is the sent row's guid. Removals (3000-3006) cancel the
    matching reaction.
  - Tapback display text, including the quoted message, is kept out of the keyword match. Only plain-text tapbacks
    leak in (see L3).
- **Claude Code config:**
  - The project's `allowedTools` is empty, and `~/.claude/settings.json` doesn't mention imessage.
  - Only `imessage-demo` is registered, with the demo DB and contacts and no LIVE flag.

## Summary

The send path does what the spec promises on the points that matter most:
- Nothing reaches Messages without Blake clicking Send in a dialog whose default is Cancel.
- Phone and text never touch the AppleScript source.
- The echo check and single-use tokens hold.
- No tool can read or text a number outside `contacts.csv`.

The serious gaps are both about **double texts**. H1 is the main one: a SQLite or log error after osascript has sent
the text leaves no log record, so a retry passes the duplicate guard (reproduced). M1: two overlapping
`confirm_send`s each show a dialog and send, because nothing serializes them and the guards aren't re-run after Send
(reproduced). M2 is a documentation fix: the dialog is only a human gate when the session doesn't have computer-use
control and isn't in auto mode. The rest are low-impact accuracy issues: the allowlist isn't re-checked at confirm,
`ok` stays true for unknown rows, the keyword guess has false hits, and text-style SMS tapbacks aren't recognized.

The first live send to a spouse or friend is reasonable as is. Before texting ward members, fix H1 (log before
sending, and turn SQLite errors into ChatDBError) and M1 (one send lock, and re-check after the dialog).
